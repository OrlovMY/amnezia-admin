# Выпуск релиза (порядок для владельца)

**Выполнять только после живой приёмки стека (`ПРИЁМКА-ВЛАДЕЛЬЦЕМ.md`) и
слияния PR-1…PR-6б в `main` (`--no-ff`, порядок стека). До этого ничего
ниже не делать.**

Этот файл — для владельца, порядок первого (и последующих) релизов.
`README.md` — для пользователей публичного репозитория, там про сборку из
исходников и версию.

Везде ниже `<владелец>` — ваш логин на GitHub, замените один раз перед
началом. Каждый шаг — команда и то, что должно получиться.

## 1. История на секреты

Публичный репозиторий отдаёт всю историю целиком, не только текущий `main`.
Перед тем как её кто-либо увидит — проверить, что в ней никогда не было
секретов.

```sh
git -c core.quotePath=false log --all --name-only --format= | sort -u | grep -E '\.avlt$|\.conf$|Настройки/|Конфигурации/|throttle\.json|ui\.json|crash\.log'
```

Допустимы только `core/testdata/v1.avlt` и `core/testdata/v2.avlt`
(golden-фикстуры для тестов, внутри — заведомо фиктивный
`vpn://golden-fixture-key`). Любое другое имя в выводе — стоп, не
публиковать, звать ядро.

```sh
git -c core.quotePath=false log main -p | grep -cE 'vpn://[A-Za-z0-9_-]{60,}|BEGIN [A-Z ]*PRIVATE KEY'
```

Ожидается `0`. Ненулевое значение — посмотреть найденные строки
(`git ... log main -p | grep -nE '...'`) и убедиться, что это фикстуры
(`golden-fixture-key`, тестовые ключи `cmd/fakeserver`/`internal/fakesrv`),
а не боевой ключ. Если сомневаетесь хоть немного — **не публикуйте**,
зовите ядро.

*(Обе команды и подсадка `printf 'Настройки/x\n' | grep -E 'Настройки/'`
прогнаны исполнителем на ветке `feat/pr6b-release` — 0 в истории main,
только две golden-фикстуры в списке имён, подсадка поймана. Прогоните
снова сами на итоговом `main` после слияния стека — состав истории мог
измениться.)*

## 2. Авторизация GitHub CLI

```sh
gh auth login
```

Интерактивно, следуйте подсказкам `gh`.

## 3. Создать репозиторий

```sh
gh repo create <владелец>/amnezia-admin --public --description "Утилита администрирования сервера Amnezia VPN (AmneziaWG / WireGuard) через SSH"
```

Без `--source`/`--push` — репозиторий создаётся пустым, код заливается
позже отдельным шагом (6), по имени ветки, без тегов.

## 4. Настройки репозитория руками

В веб-интерфейсе GitHub (или `gh api`, если удобнее):

- **Settings → Actions → General → Workflow permissions** — «Read
  repository contents permission» (минимум; `release.yml` сам поднимает
  `contents: write` только для задания `release`, см.
  <https://docs.github.com/en/actions/security-guides/automatic-token-authentication>).
- **Settings → Rules → Rulesets** — новый ruleset, target **Tags**,
  паттерн `v*`: запретить создание (`Creation`), удаление (`Deletion`) и
  перезапись без быстрой перемотки (`Update` → block force-push/
  non-fast-forward) всем, кроме вас как администратора в списке bypass
  (<https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets>).
  Это закрывает чужие учётки и токены, включая появление постороннего
  `v0.0.1` — но не защищает от вашего собственного `git push` тега не с
  `main` (см. шаг 6).
- **Settings → Code security → Dependabot alerts** — включить.

Проверка ruleset:

```sh
gh api repos/<владелец>/amnezia-admin/rulesets
```

В ответе должен быть ruleset с `"target": "tag"`.

## 5. Remote: GitHub + GitLab-зеркало

Сначала убедиться, что тега `v0.0.1` нигде нет:

```sh
git ls-remote --tags origin
git tag -l 'v*'
```

`git ls-remote --tags origin` — только `archive/v0.0.1-pre-audit` (тег
`v0.0.1` удалён на GitLab 15.09.2026), `git tag -l 'v*'` — пусто. Иное —
стоп, звать ядро, дальше не идти.

Если в вашем локальном клоне `git tag -l v0.0.1` **не пусто** (клон
старый, тег ещё существовал у вас на момент клонирования) —

```sh
git tag -d v0.0.1
```

только локально (объект уже сохранён на GitLab под именем
`archive/v0.0.1-pre-audit`, ничего не теряется), и из этого клона не
пушить, пока `git tag -l v0.0.1` не станет пустым.

GitLab остаётся зеркалом: один push пишет в оба remote.

```sh
git remote set-url --add --push origin git@gitlab.thedatum.one:devops/tools/personal/orlov/amnezia-admin.git
git remote set-url --add --push origin git@github.com:<владелец>/amnezia-admin.git
```

Первая команда обязательна и первая по порядку: без неё второе
`--add --push` заменило бы push-адрес `origin` по умолчанию, а не
добавило второй.

```sh
git remote -v
```

У `origin` должна быть одна строка `(fetch)` и **две** строки `(push)`.
Плюс отдельный remote только для чтения (проверки `ls-remote` ниже):

```sh
git remote add github git@github.com:<владелец>/amnezia-admin.git
```

## 6. Push `main` — сначала ветка, потом тег

**Порядок обязателен** (ядро, п.2): сначала `main` по имени, отдельным
push, без тегов. Тег без `main` на GitHub — шаг «Происхождение тега» в
`release.yml` отклонит его же собственным workflow (тег ещё не был бы
предком `origin/main`).

Перед push — три проверки:

```sh
git config --get push.followTags
git tag -l 'v*'
git ls-remote --tags github
```

Первая — пусто или `false` (иначе `push` мог бы утащить теги вместе с
веткой, если он у вас глобально включён); вторая и третья — пусто.

```sh
git push --no-follow-tags origin main
```

**Никогда** `--all`, `--tags`, `--mirror`, `--follow-tags` — любой из них
рискует утащить старый `v0.0.1`, если он всё ещё где-то в ваших
локальных тегах.

После push:

```sh
git ls-remote --tags github
git ls-remote --tags origin
```

Первая — пусто (на GitHub тегов ещё нет), вторая — только
`archive/v0.0.1-pre-audit` (GitLab не менялся).

## 7. Первый релиз — rc-тег

```sh
git tag -a v0.1.0-rc.1 -m "amnezia-admin 0.1.0-rc.1"
git ls-remote --tags github
```

Вторая команда — пусто (тег ещё не отправлен). Теперь отправляем:

```sh
git push --no-follow-tags origin v0.1.0-rc.1
git ls-remote --tags github
```

Ожидается ровно `v0.1.0-rc.1`. Push тега запускает `release.yml` на
GitHub (Actions → вкладка репозитория).

## 8. Проверка прогона

В Actions (вкладка репозитория на GitHub):

1. Задания `test` → `build` → `release` — все зелёные, в этом порядке.
2. Релиз на странице Releases помечен **Pre-release**.
3. У релиза ровно **девять** ассетов: 8 бинарей + `SHA256SUMS`.
   Пять консольных:
   - `amnezia-admin-linux-amd64`
   - `amnezia-admin-linux-arm64`
   - `amnezia-admin-windows-amd64.exe`
   - `amnezia-admin-macos-amd64`
   - `amnezia-admin-macos-arm64`

   Три графических:
   - `amnezia-admin-gui-linux-amd64`
   - `amnezia-admin-gui-windows-amd64.exe`
   - `amnezia-admin-gui-macos-arm64`
4. Скачать все девять в пустой каталог и проверить:
   ```sh
   sha256sum -c SHA256SUMS
   ```
   Ожидается восемь строк `OK`.
5. Версия в CLI-бинаре:
   ```sh
   amnezia-admin-windows-amd64.exe version
   ```
   Ожидается **точное** совпадение (без единого лишнего символа):
   ```
   amnezia-admin v0.1.0-rc.1 (<sha7>)
   ```
   где `<sha7>` — первые 7 символов коммита, на который указывает тег
   (не хэш самого тега как объекта — тег аннотированный, это разные
   вещи):
   ```sh
   git rev-parse --short=7 v0.1.0-rc.1^{commit}
   ```
   Версия проверяется на том бинаре, который подходит вашей машине:
   запустить все восемь негде — у вас нет ни Linux-arm64, ни Intel-мака,
   и это нормально. Версию всех восьми, включая только что проверенный
   вами, до этого уже проверил CI — двумя разными шагами: пять консольных
   в шаге «Проверка версии — CLI» (три нативные для своего раннера —
   запуском с посимвольным сравнением вывода, две кросс-собранные —
   по телу бинаря и `go version -m`), три графических — в шаге «Проверка
   версии — GUI» (GUI не печатает версию в stdout, поэтому она ищется
   как строка внутри бинаря).
6. Заголовок окна GUI (`amnezia-admin-gui-windows-amd64.exe`) содержит
   `v0.1.0-rc.1` — откройте программу и посмотрите на заголовок окна и
   на экран подключения (версия напечатана и там, и там). Сделайте
   **скриншот заголовка окна** — приложите к записи о релизе в
   `resume-2026-09-14.md`/аналогичный журнал, как доказательство для
   ядра, что версия действительно дошла до конечного бинаря.

Рекомендуется, не блокирует выпуск (ядро, п.4):

```sh
gh attestation verify amnezia-admin-windows-amd64.exe --repo <владелец>/amnezia-admin
```

Успех — хорошо. Неуспех — запишите и сообщите ядру, сам rc не отзывайте
из-за одной этой проверки.

## 9. Если что-то упало

- Шаг **«Происхождение тега» упал с «не на origin/main»** — значит, либо
  `main` ещё не был отправлен (шаг 6), либо тег случайно поставлен не на
  вершину `main`. Решение: отправить `main` (шаг 6), затем нажать
  **Re-run jobs** в Actions для того же прогона. **Тег не пересоздавать**
  — ядро явно запретило это как отдельное решение (п.2): пересоздание
  тега на новый коммит после публичного push — путаница для всех, кто
  уже мог его увидеть.
- Упало что-то другое (тесты, сборка, состав активов) — тег этого rc
  считается неудачным. Не удаляйте pre-release и не пересоздавайте тег
  задним числом — это разрушительные операции, делать их можно только
  осознанно и вручную, не по этой инструкции. Вместо этого: почините
  причину падения обычным PR через ветку и слияние в `main`, затем
  выпустите следующий `v0.1.0-rc.2` шагами 7–8. **Номер rc только
  растёт** — `scripts/check-version-growth.sh` в CI отклонит повторную
  попытку тем же `v0.1.0-rc.1` (случай 6 в таблице проверок скрипта:
  повтор существующего тега — отказ) и понижение номера; после
  неудачного `rc.1` следующая попытка — всегда `rc.2`, а не повтор
  `rc.1`, даже если `rc.1` не был опубликован из-за падения.

## 10. Финальный релиз

Когда rc полностью зелёный и проверен (шаг 8) — финальный релиз теми же
шагами 7–8, но без `-rc.N`:

```sh
git tag -a v0.1.0 -m "amnezia-admin 0.1.0"
git push --no-follow-tags origin v0.1.0
```

Он уже не будет помечен Pre-release. Номер `0.1.0` — предложение
исполнителя, финальное решение о номере — за вами.

## Отступление от `deploy-provenance-and-build-integrity.md` п. 1

Стандарт не правится, но для этого продукта — десктопной утилиты без
сервера деплоя — решение ядра 15.09.2026: номер версии живёт не в коде
(нет файла VERSION, нет константы в исходниках), а в git-теге
`vX.Y.Z[-rc.N]`. Монотонность и происхождение обеспечивают: CI
(`release.yml` — semver-шаблон и строгий рост над последним `v*` тегом
через `scripts/check-version-growth.sh`, тег обязан быть предком
`origin/main`) и ruleset на теги `v*` в GitHub (шаг 4 выше — запрет
создания/удаления/перезаписи не-владельцем). Пункты 4–5 стандарта
(версия из тега вшита в бинарь, тег неизменяем) выполняются этим же
механизмом.
