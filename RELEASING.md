## 1. История на секреты

Публичный репозиторий отдаёт всю историю целиком, не только текущий `main`.
Перед тем как её кто-либо увидит — проверить, что в ней никогда не было
секретов.

```sh
git -c core.quotePath=false log --all --name-only --format= | sort -u | grep -E '\.avlt$|\.conf$|Настройки/|Конфигурации/|throttle\.json|ui\.json|crash\.log'
```

Допустимы только три golden-фикстуры для тестов:

- `core/testdata/v1.avlt` и `core/testdata/v2.avlt` — внутри заведомо
  фиктивный `vpn://golden-fixture-key`;
- `core/testdata/shortpin.avlt` (с A4, 19.09.2026) — хранилище со старым
  10-символьным пином для тестов перезапечатывания; внутри фиктивный
  `vpn://oldshortpin-fixture`, пин записан в `core/vault_shortpin_test.go`.

Любое другое имя в выводе — стоп, не публиковать, звать ядро.

Ключи и ссылки `vpn://` — одной командой, по той же области `--all`, что
и список имён выше:

```sh
bash scripts/check-history-keys.sh
```

Ожидается код выхода `0` и строки:

```
канарейка: 8 образцов опознаны как ожидалось
область: git log --all -p
PEM-заголовков приватного ключа: 14 (записано: 14)
блоков с телом ключа (подозрительных): 0
длинных ссылок vpn://: 0
```

Коды выхода:

- **`1`** — рядом с заголовком найдено тело ключа или в истории есть
  длинная ссылка `vpn://`. Печатаются заголовок и номер строки, тело
  не печатается никогда. Не публиковать, звать ядро.
- **`2`** — канарейка: скрипт не опознал собственные образцы (ключ файлом,
  тело по 40, тело с пробелами, зашифрованный PEM, короткий ключ EC, ключ
  одной строкой) или принял за ключ синтетику. Результату верить нельзя,
  не публиковать.
- **`3`** — число PEM-заголовков не равно записанному в скрипте
  (`KNOWN_HEADERS`). Тела рядом скрипт не нашёл, но ключ, который он не
  узнаёт, выглядит так же. **Настоящий ключ с телом строками короче 16
  символов или в base64url (`-` и `_` вместо `+` и `/`) даёт не `1`, а
  именно `3`** — не принимайте код 3 за «просто сменились тесты».
  Посмотрите новые места:
  `git -c core.quotePath=false log --all -p | grep -nE 'BEGIN [A-Z ]*PRIVATE KEY'`.
  Если это тесты, обновите `KNOWN_HEADERS` отдельным коммитом, и только
  тогда продолжайте. Сомневаетесь — **не публикуйте**, зовите ядро.

Почему не `grep -c 'BEGIN … PRIVATE KEY'` с ожиданием `0`, как было
раньше. Тесты маскировки (`core/runner_mask_test.go`) содержат
синтетические PEM-заголовки — строки в Go-коде, тела у них
`test-pem-body-…`, настоящих ключей нет. Счёт давал `14` и ложное «не
публиковать» на каждом релизе. Скрипт различает по существу: собирает
символы base64 от заголовка до `END` (не дальше 100 строк и не через
границу коммита) и считает блок ключом от 100 символов. Как именно — в
шапке скрипта.

**Чего эта проверка НЕ видит — и прежняя не видела тоже:**

- ключ без заголовка `BEGIN … PRIVATE KEY`: голое тело base64, PuTTY
  `.ppk`, ключи в других форматах;
- бинарные файлы: `git log -p` пишет про них только «Binary files
  differ»;
- содержимое, которое есть только в диффе merge-коммита: `git log -p`
  диффов слияний не показывает;
- ссылку `vpn://` короче 60 символов после схемы.

Список имён выше закрывает часть этого (`.avlt`, `.conf`, каталоги
данных) по имени файла, но не по содержимому.

*(Прогнано исполнителем A6 29.09.2026 в worktree на ветке
`fix/a6-release-chain`: три фикстуры в списке имён; скрипт — выход `0`,
14 заголовков, 0 подозрительных, 0 `vpn://`. Во временных репозиториях с
настоящими ключами openssl/ssh-keygen (RSA PEM, зашифрованный PEM, EC
P-256, ed25519, CRLF, тело по 40, пробелы каждые 20, YAML с отступом,
Go-литерал) — выход `1` во всех девяти случаях; один синтетический
заголовок — выход `3`. Прогоните снова сами на итоговом `main` — состав
истории мог измениться.)*

## 4. Настройки репозитория руками

В веб-интерфейсе GitHub (или `gh api`, если удобнее):

- **Settings → Actions → General → Workflow permissions** — «Read
  repository contents permission» (минимум; `release.yml` сам поднимает
  `contents: write` только для задания `release`, см.
  <https://docs.github.com/en/actions/security-guides/automatic-token-authentication>).
- **Settings → Rules → Rulesets** — новый ruleset, target **Tags**,
  паттерн `v*`: запретить создание (`Creation`), удаление (`Deletion`) и
  перезапись без быстрой перемотки (`Update` → block force-push/
  non-fast-forward) всем, кроме вас как администратора в списке bypass
  (<https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets>).
  Это закрывает чужие учётки и токены, включая появление постороннего
  `v0.0.1` — но не защищает от вашего собственного `git push` тега не с
  `main` (см. шаг 6).
- **Settings → Code security → Dependabot alerts** — включить.

Проверка ruleset:

```sh
gh api repos/<владелец>/amnezia-admin/rulesets
```

В ответе должен быть ruleset с `"target": "tag"`.

## 5. Remote: GitHub + GitLab-зеркало

Сначала убедиться, что тега `v0.0.1` нигде нет:

```sh
git ls-remote --tags origin
git tag -l 'v*'
```

`git ls-remote --tags origin` — только `archive/v0.0.1-pre-audit` (тег
`v0.0.1` удалён на GitLab 15.09.2026), `git tag -l 'v*'` — пусто. Иное —
стоп, звать ядро, дальше не идти.

Если в вашем локальном клоне `git tag -l v0.0.1` **не пусто** (клон
старый, тег ещё существовал у вас на момент клонирования) —

```sh
git tag -d v0.0.1
```

только локально (объект уже сохранён на GitLab под именем
`archive/v0.0.1-pre-audit`, ничего не теряется), и из этого клона не
пушить, пока `git tag -l v0.0.1` не станет пустым.

GitLab остаётся зеркалом: один push пишет в оба remote.

```sh
git remote set-url --add --push origin git@gitlab.thedatum.one:devops/tools/personal/orlov/amnezia-admin.git
git remote set-url --add --push origin git@github.com:<владелец>/amnezia-admin.git
```

Первая команда обязательна и первая по порядку: без неё второе
`--add --push` заменило бы push-адрес `origin` по умолчанию, а не
добавило второй.

```sh
git remote -v
```

У `origin` должна быть одна строка `(fetch)` и **две** строки `(push)`.
Плюс отдельный remote только для чтения (проверки `ls-remote` ниже):

```sh
git remote add github git@github.com:<владелец>/amnezia-admin.git
```

## 6. Push `main` — сначала ветка, потом тег

**Порядок обязателен** (ядро, п.2): сначала `main` по имени, отдельным
push, без тегов. Тег без `main` на GitHub — шаг «Происхождение тега» в
`release.yml` отклонит его же собственным workflow (тег ещё не был бы
предком `origin/main`).

Перед push — три проверки:

```sh
git config --get push.followTags
git tag -l 'v*'
git ls-remote --tags github
```

Первая — пусто или `false` (иначе `push` мог бы утащить теги вместе с
веткой, если он у вас глобально включён); вторая и третья — пусто.

```sh
git push --no-follow-tags origin main
```

**Никогда** `--all`, `--tags`, `--mirror`, `--follow-tags` — любой из них
рискует утащить старый `v0.0.1`, если он всё ещё где-то в ваших
локальных тегах.

После push:

```sh
git ls-remote --tags github
git ls-remote --tags origin
```

Первая — пусто (на GitHub тегов ещё нет), вторая — только
`archive/v0.0.1-pre-audit` (GitLab не менялся).

## 6а. A3б: отпечаток записи совпадает с проверенным на канарейке

Канарейку A3б владелец прогоняет на ревизии ветки, а выпуск идёт из коммита
после слияния в `main`. Поэтому перед rc-тегом, в котором есть A3б, сверяются
три суммы команды записи:

```sh
git checkout <выпускаемая ревизия>
git status                      # «working tree clean»
go build -o canary-a3b ./cmd/canary-a3b
./canary-a3b -print-fingerprint
```

Программа не подключается к серверу и печатает ревизию и строку
`sha256(CASWriteScript)=… sha256(CASWriteCommand)=… sha256(CASWriteCommandSudo)=…`.
Три суммы обязаны посимвольно совпасть с тремя суммами из строки `П2` вывода
канарейки, присланного владельцем. **Не совпала хоть одна — текст записи на
сервере изменился после проверки: канарейку прогнать заново на выпускаемой
ревизии, тег не ставить.** Ревизии при этом могут различаться — сверяется
текст команды, а не номер коммита.

**После PR-W1 отпечаток новый.** Имя файла конфигурации стало аргументом `$4`
скрипта записи (`cf=$4`, семейство WG: `wg0.conf` у amnezia-awg и
amnezia-wireguard, `awg0.conf` у amnezia-awg2). Суммы прогонов канарейки до
W1 недействительны. Сверять с прогоном на верхушке ветки выпуска
`fix/awg-protocols` (сведение W2 + W3, К2–К8). На ней (02.10.2026, финальный
раунд сведения) суммы такие — те же, что на `fix/w3-awg2`: сведение и
финальный раунд команду записи не меняли:

```
sha256(CASWriteScript)=983c91951d8816d64f0cfd57075eb637b57726e09fdc4721cc5da6d7263fae67
sha256(CASWriteCommand)=a71c77fe3849170b8aa3d3ea741c07b83a1132934870b27a862a1c7e182b3b27
sha256(CASWriteCommandSudo)=470a1c657646f7591751f157a0c71a8e57a124af63d780fffed5482e5081cc8b
```

Эти суммы — для справки. Решает строка `П2` из присланного вывода, а не этот
файл.

**После Р-4 (ветка `feat/backup-migrate`, 04.10.2026) отпечаток снова новый.**
Скрипт записи принимает после `$4` пары «имя сумма» дополнительных файлов из
закрытого списка (ключи XRay при `server.json`; `wireguard_server_public_key.key`
и `wireguard_psk.key` при `wg0.conf`/`awg0.conf`), а отпечаток команды теперь
снимается с заглушкой `server.json` и всеми четырьмя ключами XRay — хвост
команды тоже под отпечатком. Суммы прогонов до Р-4 недействительны. Новые
шаги канарейки — К9 (запись с ключами под замком) на `amnezia-xray` и на
каждом проверяемом контейнере семейства WG; `amnezia-xray` пропускается
только флагом `-skip-family amnezia-xray` (итог тогда ПРОЙДЕН ЧАСТИЧНО).
Суммы на верхушке ветки до канарейки:

```
sha256(CASWriteScript)=e5436390a3f7515c97d3a20ed07303b1d0c05bd297186df69bff802c8315d551
sha256(CASWriteCommand)=c9bf1085fead222400e645a7a21f3f2c2071954a40b53c7b1d0ebede815beb86
sha256(CASWriteCommandSudo)=90be3a111d1c92d41caa59d27ac4c2c08c4bc936fd106d3e96d38d527fb960f6
```

**Флаги канарейки после W1/W3:**
- `-server-ip <IP>` — IP тестового сервера из панели провайдера; сверяется с
  адресом из ключа до подключения (имя в ключе — флаг обязан быть среди его
  адресов), не совпал — отказ; дальше канарейка и дочерние программы
  подключаются ПРЯМО по этому IP (второй фактор вместе с `-not-production`).
  С ним до первой записи — предпроверка сервера: «П0-свежесть» (каждый
  контейнер Amnezia не старше 72 ч, `docker inspect .Created`; сбой — СТОП,
  флагом не обходится) и «П0-сервер» (существующих клиентов по всем
  контейнерам WG в сумме не больше трёх). Снимки существующих клиентов
  сверяются в конце шагом «П0-итог». Без флага сервер обязан быть пуст.
  **Граница:** `.Created` — возраст КОНТЕЙНЕРА, а не сервера. Если на боевом
  сервере протокол переустановлен за последние 72 ч, «П0-свежесть» пройдёт;
  тогда защищают порог (не больше трёх клиентов на сервер) и `-server-ip`.
- `AMNEZIA_KEY_SUDO` (второй ключ, по нему пишет PR4.2) обязан вести на тот же
  сервер: с `-server-ip` — закрепляется тем же IP, без флага — хост и порт
  обязаны совпасть с основным ключом, иначе отказ до подключения.
- `-container <имя>` — проверять один контейнер семейства WG. По умолчанию
  проверяются все найденные.
- `-old` (v0.2.0) нужен только для шага К7 на amnezia-awg. Контроль гонки К4
  канарейка теперь выполняет сама, прежней командой записи без замка. На
  amnezia-awg2 К7 — «НЕ ПРИМЕНИМО»: v0.2.0 этот контейнер не знает.
- Обязательные семейства — amnezia-awg и amnezia-awg2. Если какого-то нет на
  сервере (или оно не выбрано `-container`), итог — НЕ ПРОВЕРЕНО.
  `-skip-family <имя>` пропускает семейство осознанно. Итог тогда —
  отдельное состояние: первая строка «ИТОГ: ПРОЙДЕН ЧАСТИЧНО — без живой
  проверки: …», код выхода 3 (не 0). **Выпуск по частичному итогу — только с
  явным решением владельца, записанным в заметке к выпуску (кто, когда,
  какое семейство вживую не проверено).** Без такой записи частичный итог
  равен «НЕ ПРОВЕРЕНО»: тег не ставить.
- Шаг П4 сверяет монтирования `/opt/amnezia/awg` у amnezia-awg и amnezia-awg2.
  Общий каталог хоста — СТОП.
- К8 печатает строку «Вариант AWG: проверено на AWG3; AWG2 — только на
  тестовом стенде» (или наоборот). Её переносят в заметку к выпуску.

Собирать не из вложенного git worktree: `go build` в worktree внутри другого
клона записывает ревизию внешнего клона (замечено 01.10.2026), и строка
`vcs.revision` будет неверной. Суммы от этого не зависят.

В Actions (вкладка репозитория на GitHub):

2. Релиз на странице Releases помечен **Pre-release**.

   Пять консольных:

   - `amnezia-admin-gui-linux-amd64`
   - `amnezia-admin-gui-windows-amd64.exe`
   - `amnezia-admin-gui-macos-arm64`
4. Скачать все девять в пустой каталог и проверить:
   ```sh
   sha256sum -c SHA256SUMS
   ```
   Ожидается восемь строк `OK`.
5. Версия в CLI-бинаре:
   ```sh
   amnezia-admin-windows-amd64.exe version
   ```
   Ожидается **точное** совпадение (без единого лишнего символа):
   ```
   amnezia-admin v0.1.0-rc.1 (<sha7>)
   ```
   где `<sha7>` — первые 7 символов коммита, на который указывает тег
   (не хэш самого тега как объекта — тег аннотированный, это разные
   вещи):
   ```sh
   git rev-parse --short=7 v0.1.0-rc.1^{commit}
   ```
   Версия проверяется на том бинаре, который подходит вашей машине:
   запустить все восемь негде — у вас нет ни Linux-arm64, ни Intel-мака,
   и это нормально. Версию всех восьми, включая только что проверенный
   вами, до этого уже проверил CI — двумя разными шагами: пять консольных
   в шаге «Проверка версии — CLI» (три нативные для своего раннера —
   запуском с посимвольным сравнением вывода, две кросс-собранные —
   по телу бинаря и `go version -m`), три графических — в шаге «Проверка
   версии — GUI» (GUI не печатает версию в stdout, поэтому она ищется
   как строка внутри бинаря).
6. Заголовок окна GUI (`amnezia-admin-gui-windows-amd64.exe`) содержит
   `v0.1.0-rc.1` — откройте программу и посмотрите на заголовок окна и
   на экран подключения (версия напечатана и там, и там). Сделайте
   **скриншот заголовка окна** — приложите к записи о релизе в
   `resume-2026-09-14.md`/аналогичный журнал, как доказательство для
   ядра, что версия действительно дошла до конечного бинаря.
7. Проверка окружения на своей машине:
   ```sh
   amnezia-admin check
   ```
   Ожидается одна из двух итоговых строк — обе означают «всё в порядке»:
   ```
   Графический интерфейс запустится.
   ```
   ```
   Всё необходимое на месте: графический интерфейс запустится — но запускать его нужно на своём компьютере, с графическим рабочим столом, а не отсюда.
   ```
   Вторая появляется, когда проверку выполняют по SSH: графической сессии
   на сервере нет, и это нормально. Любой другой итог — находка: запишите
   вывод целиком и сообщите ядру.
   Это единственная проверка релиза, которую выполняют на реальном
   Linux: у исполнителя Linux-машины нет вовсе, и все остальные
   утверждения о Linux-окружении опираются на тесты с подставными
   данными.

Рекомендуется, не блокирует выпуск (ядро, п.4):

```sh
gh attestation verify amnezia-admin-windows-amd64.exe --repo <владелец>/amnezia-admin
gh attestation verify SHA256SUMS --repo <владелец>/amnezia-admin
```

Вторая строка — с A6: до него `SHA256SUMS` не входил в аттестацию, и
на релизах до A6 она ожидаемо даст неуспех. На первом rc после A6 её успех
— единственное доказательство, что файл сумм действительно подписан.

Успех — хорошо. Неуспех — запишите и сообщите ядру, сам rc не отзывайте
из-за одной этой проверки.

## 9. Если что-то упало

- Шаг **«Происхождение тега» упал с «не на origin/main»** — значит, либо
  `main` ещё не был отправлен (шаг 6), либо тег случайно поставлен не на
  вершину `main`. Решение: отправить `main` (шаг 6), затем нажать
  **Re-run jobs** в Actions для того же прогона. **Тег не пересоздавать**
  — ядро явно запретило это как отдельное решение (п.2): пересоздание
  тега на новый коммит после публичного push — путаница для всех, кто
  уже мог его увидеть.
- Упало что-то другое (тесты, сборка, состав активов) — тег этого rc
  считается неудачным. Не удаляйте pre-release и не пересоздавайте тег
  задним числом — это разрушительные операции, делать их можно только
  осознанно и вручную, не по этой инструкции. Вместо этого: почините
  причину падения обычным PR через ветку и слияние в `main`, затем
  выпустите следующий `v0.1.0-rc.2` шагами 7–8. **Номер rc только
  растёт** — `scripts/check-version-growth.sh` в CI отклонит повторную
  попытку тем же `v0.1.0-rc.1` (случай 6 в таблице проверок скрипта:
  повтор существующего тега — отказ) и понижение номера; после
  неудачного `rc.1` следующая попытка — всегда `rc.2`, а не повтор
  `rc.1`, даже если `rc.1` не был опубликован из-за падения.

## 10. Финальный релиз

Когда rc полностью зелёный и проверен (шаг 8) — финальный релиз теми же
шагами 7–8, но без `-rc.N`:

```sh
git tag -a v0.1.0 -m "amnezia-admin 0.1.0"
git push --no-follow-tags origin v0.1.0
```

Он уже не будет помечен Pre-release. Номер `0.1.0` — предложение
исполнителя, финальное решение о номере — за вами.

## Отступление от `deploy-provenance-and-build-integrity.md` п. 1

Стандарт не правится, но для этого продукта — десктопной утилиты без
сервера деплоя — решение ядра 15.09.2026: номер версии живёт не в коде
(нет файла VERSION, нет константы в исходниках), а в git-теге
`vX.Y.Z[-rc.N]`. Монотонность и происхождение обеспечивают: CI
(`release.yml` — semver-шаблон и строгий рост над последним `v*` тегом
через `scripts/check-version-growth.sh`, тег обязан быть предком
`origin/main`) и ruleset на теги `v*` в GitHub (шаг 4 выше — запрет
создания/удаления/перезаписи не-владельцем). Пункты 4–5 стандарта
(версия из тега вшита в бинарь, тег неизменяем) выполняются этим же
механизмом.
